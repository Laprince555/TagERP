# Functional Permissions Engine

Answers "which screens/actions can this user open", independent of which data rows they'd see
once inside (that's [data-scope.md](data-scope.md)). Built entirely on `spatie/laravel-permission`
(already installed, unused before this engine) — Spatie remains the system of record at read
time, so every `$user->can()`, `@can`, and policy check keeps working unmodified.

## Why generate instead of hand-write

The Dynamic Table / Dynamic Record View / navigation-tree engines already call
`auth()->user()->can($application->permission_name)` everywhere — that hook existed before this
engine and was simply never fed real permission names. Building this engine was mostly about
**answering the question the UI was already asking**, not adding a new layer.

Every `modules`/`sub_modules`/`applications` row already carries a hierarchical `code`
(`fin-gl-jou`, generated by `RecordCodeBuilder` — see `.ai/rules/code-field-hierarchy.md`).
Permission names are derived directly from that code, so there is never a second naming scheme
to keep in sync by hand.

## `php artisan permissions:sync`

Run after seeding any new `Module`/`SubModule`/`Application` row.

- **Modules & sub-modules** get exactly two actions: `{code}.view`, `{code}.update`.
- **Applications** get six standard actions — `view`, `create`, `update`, `delete`, `export`,
  `print` — plus whatever `custom_actions` (a `json` column on `applications`) the Application
  declares, e.g. `post` for a journal-entry Application.
- Stamps `permission_name = "{code}.view"` on every row (used by
  `RecordReferenceAccess::applicationAccessible()` and `NavigationTreeService` to gate the page
  and filter the sidebar at all three levels).
- Idempotent — safe to re-run; only creates permissions that don't already exist, and calls
  `PermissionRegistrar::forgetCachedPermissions()` once at the end.

```php
// Declaring a custom action on an Application:
Application::create([..., 'custom_actions' => ['post']]);
// permissions:sync then creates fin-gl-jou.post alongside the six standard ones.
```

## Grant tables

Four tables, all under `Modules/HR/Database/Migrations/`. A user's effective permission set is
the **union** of every applicable row across all four:

| Table | Grants to | Notes |
|---|---|---|
| `department_permissions` | Everyone in a department | Direct grants only — **not** inherited down the department tree (a child department doesn't silently gain the parent's module access; see [data-scope.md](data-scope.md#departments-are-a-shared-catalog)) |
| `job_title_permissions` | Everyone holding a job title, any grade | The baseline every grade of a title gets |
| `job_title_grade_permissions` | Holders of a job title **at or above** a grade | Comparison is always within the same `job_title_id`'s own grade ladder — a senior in one title is never compared to a senior in another. E.g. "General Accountant" @ senior gets `fin-gl-jou.post`; junior does not |
| `job_title_grade_roles` | A named Spatie **role** (e.g. `finance_manager`) to holders of a job title, optionally grade-gated (`job_grade_id` nullable = every grade) | For roles the business names explicitly ("Finance Manager"), not just raw permissions |

## `EmployeePermissionSynchronizer`

The **only** writer to `model_has_permissions` / `model_has_roles`. Runs automatically on every
`Employee::saved()` — hire, reassignment, promotion, termination all trigger a resync
unconditionally (not just on the fields that changed, since the grant tables themselves can
change independently of the employee row).

```php
app(EmployeePermissionSynchronizer::class)->sync($employee);
// or, to inspect without writing:
$target = app(EmployeePermissionSynchronizer::class)->resolve($employee); // ['permissions' => [...], 'roles' => [...]]
```

A terminated/suspended employee (`status !== 'active'`) is synced to **zero** permissions and
roles immediately — not left until their next login.

Also invalidates the navigation-tree cache on every sync
(`NavigationTreeService::invalidateCache()`) — that cache's key hashes Spatie **role** names
only, so a permission-only grant (no role attached) would otherwise leave the sidebar serving a
stale tree until an unrelated `Module`/`SubModule`/`Application` write happened to bump the
version first. This was a real bug caught by
[a dedicated test](testing.md#cache-invalidation), not a theoretical one.

## Drift reconciliation

Because the synchronizer is the *only* writer, drift can only mean a sync call was missed —
a direct DB edit to a grant table, a queued job that failed partway. `hr:permissions:reconcile`
is the backstop:

```bash
php artisan hr:permissions:reconcile              # recompute, fix, and report drift
php artisan hr:permissions:reconcile --dry-run     # report only, write nothing
```

Iterates every active, logged-in `Employee` (`chunkById(200, ...)`), compares current
Spatie state to what `EmployeePermissionSynchronizer::resolve()` computes fresh, and reports
(then optionally corrects) any mismatch. Intended to run on a schedule, not just ad hoc.

## Worked example: "General Accountant"

The example that shaped this design, now backed by a passing test suite:

1. `department_permissions`: Finance department → `fin-gl-jou.view` (everyone in Finance can
   view the ledger, regardless of title).
2. `job_title_permissions`: "General Accountant" → `fin-gl-jou.view` (redundant with #1 here,
   included for illustration — a title-level grant works even outside Finance).
3. `job_title_grade_permissions`: "General Accountant" @ Senior grade → `fin-gl-jou.post`.
   A junior holding the same title has `view` but not `post`; promoting them to Senior (a plain
   `Employee` field update) flips `post` on with no other change.
4. `job_title_grade_roles`: "Finance Manager" job title, no grade restriction → role
   `finance_manager` attached to every grade.

## What this engine deliberately does not do

- **No field-level permission table.** A field's visibility is a `Column::visible()` /
  `ViewField` callback gated by a normal `can()` check against a normal permission —
  no new mechanism was needed once the standard-actions-plus-custom-actions shape existed.
- **No per-request permission overrides / temporary grants.** A grant always comes from the
  department/job-title/grade chain; there is no "grant this one user this one permission for
  today" table. Add one only when a real requirement demands it.
